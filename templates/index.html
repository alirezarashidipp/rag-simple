4 ANN Index Zoo — how vector DBs search fast

Brute force over your current index is instant. But at millions of vectors, comparing the query against every single vector (a Flat index) gets too slow. ANN (Approximate Nearest Neighbor) indexes check a smart subset instead — slightly lower recall (recall = share of true neighbors actually found) for 10–1000× more speed. Four big families:

IVF clustering

Cluster first — then search only the nearest cells.

k-means groups all vectors into cells around centroids. A query is compared with centroids only, then searched inside the closest nprobe cells. Risk: a true neighbor hiding just across a cell border.

Used in: FAISS IndexIVFFlat · Milvus

HNSW graph

Multi-layer graph — long hops on top, precise steps below.

Top layers are sparse highways: each greedy hop jumps far. Drop a layer, repeat, and land in the true neighborhood at layer 0. Excellent speed & recall — but the whole graph lives in RAM.

Used in: Pinecone-style DBs · Qdrant · pgvector · FAISS IndexHNSWFlat

DiskANN graph + disk

Graph search that lives on SSD, not RAM.

Keeps only compressed (PQ) codes in RAM to steer the graph walk; full vectors sit on disk and just a handful get read per query. Billion-scale search on one machine — a Microsoft design.

Used in: Azure AI Search · Milvus

Tree-based space partition

Cut space in half, again and again — like 20 Questions.

KD-trees route a query down the splits into a small leaf, then check nearby leaves. Great in low dimensions, weak at 1536-d (curse of dimensionality) — Annoy compensates with a forest of random trees.

Used in: Annoy (Spotify) · scikit-learn KD/Ball-Tree

Pinecone picks and tunes the index for you behind the API. In FAISS you choose yourself — start exact, upgrade when it gets slow: IndexFlatIP → IndexIVFFlat → IndexHNSWFlat.

5 Chunking Zoo — four ways to split a document

Before embedding, text must be split. How you split decides what the retriever can ever find — a chunk is the atom of retrieval. Four families, from dumb to smart:

Fixed-size baseline

Cut every N characters, add overlap.
✓ Dead simple, fast, predictable chunk count & size ✓ Works on any text — no assumptions needed ✗ Blindly cuts sentences and ideas in the middle ✗ Ignores structure; overlap only patches the damage
How slide a window over the text: text[i : i+size], step = size − overlap, repeat to the end — exactly chunk_fixed() in app.py.
In this project: the Fixed size mode

Recursive structure-aware

Try big separators first — fall back gracefully.
✓ Respects natural boundaries whenever possible (¶ → sentence → word) ✓ The industry default — LangChain's RecursiveCharacterTextSplitter ✗ Still size-driven: related paragraphs can get separated ✗ Fragile on PDFs that lose their line breaks during extraction
How split on \n\n first; any piece still over the limit → split by \n, then ". ", then space — recurse until every piece fits.
In this project: Sentence & Paragraph modes are simple cousins of this

Semantic meaning-based

Embed sentences — cut where the topic changes.
✓ Boundaries follow meaning — chunks are self-contained ideas ✓ Shines on messy prose with no clean structure ✗ Pays embedding calls at indexing time (slower, costs $) ✗ Needs threshold tuning; chunk sizes vary wildly
How split into sentences → embed each one → compute cosine of every neighbor pair → cut where similarity drops below a threshold (e.g. mean − 1·std) → merge the runs between cuts.
Used in: LangChain SemanticChunker · LlamaIndex

Document-specific format-aware

Use the format's own structure as the knife.
✓ Best chunks when the format is known — a section, a function, a row group ✓ Each chunk is a logically complete unit ✗ One parser per format — doesn't generalize to arbitrary text ✗ Huge sections still need a fallback splitter inside
How parse the format first (Markdown headings, code AST via tree-sitter, HTML DOM) → emit one chunk per section / function / row group → store the heading path in metadata.
Used in: MarkdownHeaderTextSplitter · AST code splitters · unstructured.io

No universal winner. Rule of thumb: start recursive; if retrieval quality disappoints, try semantic; when you control the format, go document-specific. Chunking is the highest-leverage knob in RAG — bad chunks cannot be fixed by a better LLM.

6 Embedding Dimensions — how big is a meaning-vector?

An embedding is just a list of numbers; dimension = how many numbers. Each number is one axis of "meaning space". Common sizes below — memory assumes float32 (4 bytes per number):

3072text-embedding-3-large

Embedding dimension comparison
DimensionWhat it means
384a vector of 384 numbers — light and fast
768a vector of 768 numbers — the classic BERT size
1536a vector of 1536 numbers — what this project stores in Pinecone (see the Dimension card on the dashboard)
More ↑richer semantic space to separate subtle meanings — but linearly more memory, storage cost, and search time
Fewer ↓lighter and faster — not automatically better or worse; quality comes from training, not raw size

Two practical facts: (1) a 384-d model can beat a 1536-d model on real retrieval — always check benchmarks (MTEB leaderboard) instead of trusting size. (2) OpenAI's v3 models are Matryoshka-trained: pass dimensions=512 to the API and you get the first 512 numbers with most of the quality kept — the early axes carry the most meaning.

7 Hybrid Search — Fusion & Reranking

This project is vector-only. Production RAG usually runs two retrievers in parallel — vector search (meaning) and BM25 (exact keywords, names, codes) — which produces two ranked lists. Fusion merges them into one list. A reranker then polishes the final order. Two classic fusion methods:

Weighted Score Fusion score-based

Normalize both scores, then blend with a weight α.
✓ Fully tunable: α says how much you trust each retriever ✓ Keeps score magnitude information ✗ Cosine (0–1) and BM25 (unbounded) live on different scales → normalization is mandatory and fragile ✗ Best α differs per dataset; needs evaluation queries
Used in: Weaviate hybrid (alpha) · Elasticsearch

Reciprocal Rank Fusion rank-based

Ignore scores completely — sum 1/(k+rank) across lists.
✓ No score normalization — works across ANY retrievers out of the box ✓ Robust industry default (one magic k≈60, rarely tuned) ✗ Throws away score magnitudes — a 0.99 match and a 0.60 match at rank 1 look identical ✗ Less controllable than a tuned α
Used in: Elasticsearch RRF · Azure AI Search · OpenSearch
Fusion and reranking comparison
PropertyFusionReranking
Combinesmultiple ranked lists (vector + BM25)nothing — re-scores one candidate list
Howarithmetic on scores or ranksa neural cross-encoder reads query + chunk together

Rule of thumb: RRF is the safe default (nothing to normalize); switch to weighted fusion only when you have evaluation queries to tune α on. And in most RAG stacks the single biggest quality jump comes from adding a reranker (Cohere Rerank, BGE-reranker) — because a cross-encoder actually reads the chunk next to the question instead of comparing frozen vectors.

8 RAG Quality Metrics — measure before you tune

You cannot improve what you do not measure. Build a tiny eval set (30–50 pairs of question → the chunk that answers it, from your own PDFs) and re-run it after every change. The metrics, grouped by pipeline stage:

Recall@k retrieval

Was the needed chunk retrieved at all?
Measure for each eval question, check whether its gold chunk appears in the top-k results; recall = share of questions where it does.
Good / Bad ≥ 0.90 healthy · < 0.70 broken — the LLM can never use context it never received. Recall is the ceiling of your whole system.
Improve fix chunk boundaries, raise k, hybrid search (BM25 + vector), stronger embedding model.

Context Precision retrieval

Of the k chunks sent to the LLM, how many are actually relevant?
Measure judge each retrieved chunk relevant / irrelevant (human or LLM-as-judge); precision = relevant ÷ k.
Good / Bad ≥ 0.7 good · < 0.5 the context is mostly noise — irrelevant chunks actively mislead the LLM and waste tokens.
Improve add a reranker, lower k, metadata filters, drop tiny junk chunks.

MRR retrieval

How high does the first correct chunk rank?
Measure per question take 1/rank of the first correct chunk (1st → 1.0, 2nd → 0.5, 3rd → 0.33); average over the eval set.
Good / Bad ≥ 0.8 great · < 0.5 the right chunk exists but sits too deep for a top-3 pipeline to use.
Improve reranking, better chunking, query rewriting.

Faithfulness generation

Is every claim in the answer supported by the sources?
Measure LLM-as-judge (e.g. RAGAS): split the answer into atomic claims, verify each one against the retrieved context; score = supported ÷ total.
Good / Bad ≥ 0.9 required · < 0.8 the model is inventing facts — hallucination, the #1 RAG sin.
Improve stricter "only from sources / say I don't know" prompt, better context precision (reranker), require inline citations.

Answer Relevance generation

Does the answer actually address the question?
Measure LLM-judge rating, or a cheap proxy: cosine(embed(question), embed(answer)).
Good / Bad ≥ 0.8 fine · low = fluent but off-topic answers — usually a retrieval problem wearing a generation mask.
Improve better retrieval, restate the question in the prompt, query rewriting.

Latency p50 / p95 system

How long until the user sees an answer?
Measure log total ms per query — this app already shows embed / search / LLM ms on every question. Track p95 (the slow tail), not just the average.
Good / Bad < 3 s feels instant · > 10 s users leave. LLM generation almost always dominates (you saw 1875 of 2704 ms).
Improve stream tokens, smaller chat model, fewer / shorter chunks, cache repeated questions.

Cost per query system

Tokens × price, for every answered question.
Measure sum embedding + prompt + completion tokens from the API responses; multiply by model rates.
Good / Bad no universal number — watch the trend. Context bloat (sending 10 chunks when 3 suffice) is the classic leak.
Improve higher precision (3 good chunks > 10 mediocre), cheaper models, Matryoshka dimensions, caching.

Top similarity score health signal

The best cosine score per query — your live warning light.
Measure already on your dashboard: the "top score" chip after every question.
Good / Bad the absolute number means little (0.4–0.6 is normal), but consistently < 0.3 = query/document mismatch: wrong embedding model, garbage extraction, or wrong language.
Improve check PDF extraction quality, chunking, and that the embedding model fits your language and domain.

Frameworks that automate these: RAGAS, TruLens, LangSmith / Langfuse. Golden rule: change one thing (chunk size, k, model), re-run the same eval set, compare the numbers — that loop is RAG engineering.

9 RAG Troubleshooting — 15 common failures & fixes

Debug top-down: is the right chunk in the index? → is it retrieved? → does the LLM actually use it? Almost every failure lands in one of these buckets. Click to expand.

1 Answers are slow speed
Spot: total ms high in the metrics chips; LLM ms dominates (it usually does — you saw 1875 of 2704 ms).
Fix: stream the answer token-by-token, switch to a smaller/faster chat model, send fewer & shorter chunks, cache frequent questions.
2 Confident but wrong answer (hallucination) generation
Spot: claims in the answer don't appear in any displayed source; faithfulness score drops on your eval set.
Fix: harden the prompt ("answer ONLY from sources, otherwise say you don't know"), improve context precision with a reranker, require inline citations like (Source 1).
3 Retrieved chunks are irrelevant retrieval
Spot: top score consistently low (< 0.3) and the sources read off-topic.
Fix: better chunking, hybrid search (BM25 + vector), an embedding model matched to your language/domain.
4 The right chunk exists but is never retrieved retrieval
Spot: you can find the passage manually (Pinecone Browser) but it never appears in top-3 → a recall failure.
Fix: raise k then rerank down to 3, query rewriting (LLM rephrases the question), HyDE, smaller chunks.
5 Chunks cut ideas in half chunking
Spot: sources end mid-sentence; answers contain half a fact (a salary without its currency…).
Fix: sentence / paragraph / recursive splitting, add overlap, increase chunk size.
6 Chunks too big and diluted chunking
Spot: scores look fine but the LLM misses the detail buried in a wall of text; context window bloats.
Fix: smaller chunks, structure-aware splitting, reranker to surface the sharpest piece.
7 Junk chunks: headers, page numbers data
Spot: "min chunk chars" tiny after upload (you saw min = 12!), junk strings show up as sources.
Fix: drop chunks under ~50 chars, strip headers/footers/page numbers before splitting.
8 Broken PDF extraction data
Spot: extracted text has glued words, wrong order, or is empty — scanned pages return nothing.
Fix: try a better extractor (pymupdf), run OCR for scans (tesseract), normalize line breaks before chunking. Garbage in = garbage retrieved.
9 Vocabulary mismatch retrieval
Spot: user says "fire an employee", the document says "termination of employment" — scores sag although the answer exists.
Fix: hybrid BM25, LLM query expansion (add synonyms/rephrasings), a domain glossary folded into the query.
10 Exact codes & numbers not found retrieval
Spot: queries like "invoice INV-2044" or "model X-200" fail — embeddings blur exact tokens into fuzzy meaning.
Fix: the BM25 side of hybrid search handles exact strings; also store IDs in metadata and filter on them.
11 Multi-hop questions fail generation
Spot: the answer needs facts from 2+ places ("compare the 2023 and 2024 salaries") but retrieval brings only one side.
Fix: decompose into sub-questions, retrieve per sub-question, merge contexts; raise k.
12 Lost in the middle generation
Spot: with 10+ chunks in context the LLM reliably uses the first and last, ignoring the middle ones.
Fix: send only the best 3–5 chunks, order them best-first, use a reranker to pick them.
13 Stale index — documents changed ops
Spot: the answer matches an old version of the PDF, not the current one.
Fix: re-index on every change; deterministic IDs (this project's md5 of filename+strategy+index) make re-uploads overwrite instead of duplicate; delete vectors of removed files.
14 Duplicates & mixed chunking runs ops
Spot: near-identical sources appear twice; vector count larger than expected (your 165 vs 85 moment — two strategies of the same file living together).
Fix: Clear index before switching chunking settings, include the strategy in the ID, deduplicate by content hash.
15 No refusal when the answer isn't there generation
Spot: an empty or unrelated index still produces fluent answers out of thin air.
Fix: threshold on top score (e.g. < 0.25 → reply "not found in the documents"), prompt explicitly permits refusal, show scores to the user like this app does.
